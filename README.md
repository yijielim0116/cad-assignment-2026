## Context

The web API manages a movie cast database: movies, actors, and the roles actors play in movies. Everything is stored in one DynamoDB table using a single-table design, and the infrastructure is deployed with the AWS CDK to the `eu-west-1` region.

The domain has two entities and one relationship:

+ __Movie:__ movieId (number), title (string), releaseDate (string), overview (string).
+ __Actor:__ actorId (number), name (string), dateOfBirth (string), bio (string).
+ __Role:__ movieId (number), actorId (number), roleName (string), roleDescription (string).

Items are told apart by their key prefixes:

| Item | PK | SK |
|---|---|---|
| Movie | `m#movieID` | `m#movieID` |
| Actor | `a#actorID` | `a#actorID` |
| Role | `m#movieID` | `a#actorID` |

Because a role shares its movie's partition key, one `Query` on `PK = m#movieID` returns all of a movie's roles. The table is seeded at deployment with 3 movies, 5 actors and 7 roles.

## App API endpoints

Base URL: `https://{api-id}.execute-api.eu-west-1.amazonaws.com/dev`

| Method and path | Who can call it | Description |
|---|---|---|
| `GET /movies/{movieID}/roles` | Signed-in users | Get all roles in a movie. |
| `GET /movies/{movieID}/roles?actor={actorID}` | Signed-in users | Get only that actor's role in the movie (an empty list if they're not in it). |
| `GET /actors/{actorID}` | Signed-in users | Get an actor's profile (name, date of birth, bio). |
| `GET /actors/{actorID}?movie={movieID}` | Signed-in users | Get the actor's profile plus their role in that movie, if they have one. |
| `POST /movies/roles` | Administrator (API key) | Add a role. Body: `{ "movieId", "actorId", "roleName", "roleDescription" }`. |

Responses with data use the `{ "data": ... }` structure and only ever contain model data (`Movie`, `Actor`, `Role`), never raw table items.

## Auth API endpoints

Base URL: `https://{auth-api-id}.execute-api.eu-west-1.amazonaws.com/prod` (provided with the starter code).

+ `POST /auth/signup` - Register a new user (username, password, email).
+ `POST /auth/confirm_signup` - Confirm the registration with the code Cognito emails to the user.
+ `POST /auth/signin` - Sign in and receive a Cognito ID token in a `token` cookie.
+ `POST /auth/signout` - Sign out by clearing the `token` cookie. Cognito ID tokens can't be revoked, so sign-out removes the client's copy.

## Authentication and authorisation

+ __Users:__ a custom API Gateway `RequestAuthorizer` (`lambdas/auth/authorizer.ts`) reads the `token` cookie and verifies it against the Cognito user pool with `aws-jwt-verify`. A missing, invalid or expired token returns __401 Unauthorized__. On success, the Cognito username is passed to the Lambda in the request context. Both GET routes use this authorizer.
+ __Administrator:__ `POST /movies/roles` has `apiKeyRequired: true`. The key is generated by API Gateway at deployment time (`api.addApiKey`), attached to the `dev` stage through a usage plan, and its ID is printed as the `AdminApiKeyId` stack output. A missing or wrong `x-api-key` header returns __403__ "A valid admin API key is required". A user token alone is not enough to POST, and the admin key alone does not open the GETs.

## Logging

Every App API request is logged to CloudWatch by `lambdas/shared/request-logger.ts`, in the form `<username>   <path>[?query]`, e.g.

```
yijie   /movies/1234/roles
yijie   /actors/4321?movie=1234
admin   /movies/roles
```

Requests made with the admin API key are logged as `admin`, because the administrator has no Cognito username.

## Error handling

| Case | Response |
|---|---|
| Path or query ID that isn't a positive whole number (e.g. `abc`, `0`, or too large to store exactly) | 400, naming the bad parameter |
| Unknown movie or actor (in the path or in `?actor=` / `?movie=`) | 404, e.g. "Movie 9999 not found" |
| POST body that isn't valid JSON, or isn't a JSON object | 400 |
| POST body with missing or wrongly typed fields | 400, listing every problem at once |
| POST for a movie or actor that doesn't exist | 404 |
| POST for a role that already exists | 409 Conflict |
| Missing or invalid user token on a GET | 401 |
| Missing or wrong API key on the POST | 403 |
| Unknown route or unsupported method | 404 "Route not found" (instead of API Gateway's default "403 Missing Authentication Token") |
| Unexpected error | 500 "Internal server error"; the full error is logged to CloudWatch only |

The POST writes the role in a single DynamoDB `TransactWriteCommand`: two `ConditionCheck`s confirm the movie and actor exist, and the `Put` only succeeds if the role is new. This means a failed request never leaves a partly written or orphaned role.

## Code structure

+ `lib/cognito-stack.ts` - Cognito user pool and the Auth API.
+ `lib/app-api-stack.ts` - DynamoDB table and seed data, the Lambdas, the authorizer, the App API routes, gateway responses, and the admin API key with its usage plan.
+ `lambdas/app/` - one handler per App API endpoint.
+ `lambdas/shared/http.ts` - shared response helpers, ID parsing (`pathId`, `queryId`), JSON body parsing and the generic 500.
+ `lambdas/shared/db.ts` - the DynamoDB client and `getMovieItem`, `getActorItem` and `getRoleItem`, so the key layout lives in one place.
+ `lambdas/shared/model.ts` - model types, key builders and the item-to-model mappers.
+ `lambdas/shared/request-logger.ts` - request logging.

### Detailed Specification.

#### App API.

The Web API should support the following endpoints:

+ GET /movies/{movieID}/roles?[actor=actorID] - Get details of all roles for the specified movie. 
   + Support an optional query string parameter that specifies an actor ID, e.g. ?actor=4321. Only the role played by that actor in the movie should now be returned, if relevant.
+ GET /actors/{actorID}?[movie=movieID] - Return the specified actor's profile (DOB, bio, etc).
   + Support an optional query string parameter that specifies a movie ID. The response should now also include the description of the actor's role in the specified movie, if relevant. 
+ POST /movies/roles - add a movie role.

+ Actor:

#### DynamoDB table design.

The application's database will follow the *Single-table* design pattern. This means:
+ One table stores all the data (movies, actors and roles).
+ A table item could represent an entity (e.g. movie) or a relationship between entities (e.g. role). 

The table’s partition and sort keys contain entity IDs, and prefixes will be used to distinguish between the item types as follows: 

+ Movie - PK = m#movieID, SK = m#movieID.
+ Actor - PK = a#actorID, SK = a#actorID.
+ Role - PK = m#movieID, SK = a#actorID.

#### Stack Architecture.

A multi-stack architecture should be used: one stack encapsulating user authentication requirements (Cognito stack), and a separate stack containing the application Web API (App API stack).

#### Authentication. 

Two forms of authentication will be used:
+ Username and password credentials for users.
+ An API key for the administrator.

The Cognito service manages user credentials. The Cognito stack should include a separate web API (the Auth API) to handle user authentication requests. It should allow users to self-register, log in, and log out. 

The administrator authenticates using an API key instead of a username and password. The key is generated at deployment time by the API Gateway service in the App API stack.

#### Authorisation.

Only authenticated users can perform HTTP GET requests, while an authenticated administrator can perform POST requests.

#### Logging.

The application should log all user requests to CloudWatch logs. A log entry should specify the request path and the Cognito username of the requester, e.g.

+  jbloggs    /actors/4321?movie=1234
